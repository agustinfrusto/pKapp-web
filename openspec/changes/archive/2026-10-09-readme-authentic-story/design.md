## Objetivo

Mantener un estilo de documentación que refleje la verdad del proyecto: útil, honesto, concreto y construido con criterio.

## Directrices de estilo

### Tono

- Usar un tono sobrio, humano y claro.
- Priorizar la utilidad sobre la presentación.
- Evitar lenguaje promocional, de lanzamiento o de “marketing”.
- No usar frases tipo “revolucionario”, “premium”, “game-changer”, “impresionante” o similares si no aportan información útil.

### Historia del proyecto

- La introducción debe explicar que el proyecto nació para resolver un problema concreto.
- Incluir la idea de que empezó ayudando a una persona cercana y luego comenzó a ser útil para otras personas.
- Mantener la historia real sin exagerar ni “vender” la solución.

### Estructura sugerida

1. Introducción honesta
2. Qué hace el proyecto
3. Cómo se construye / Spec Driven Development
4. Características principales
5. Instalación / uso
6. Arquitectura
7. Licencia y transparencia

### Regla de formato

- El README debe leerse como una explicación útil, no como una landing page.
- Las secciones deben estar ordenadas con lógica narrativa.
- La primera parte debe decir por qué existe el proyecto y qué problema resuelve.
- La segunda parte debe describir cómo trabaja y cómo se sostiene.

### Ejemplo de frase guía

> pKapp nació como una herramienta para ayudar a una persona concreta y terminó siendo útil para muchas otras. No se construyó como un producto para “salir en una demo”; se construyó para resolver una necesidad real de estudio.

## Criterio de aceptación

La edición del README es correcta si:

- suena humana y clara;
- evita la sensación de “pitch comercial”;
- refleja la intención original del proyecto;
- mantiene la narrativa de Spec Driven Development;
- conserva la utilidad del contenido técnico.
